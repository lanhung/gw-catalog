# SIS Noisy 训练速度优化结果说明

## 1. 实验目的

本轮优化关注训练速度，而不是重新设计模型结构。目标是在保持当前 `SIS noisy + InceptionTime + ep50` 检索效果基本可用的前提下，减少训练耗时，并把不同数据规模下的速度变化记录成可复现实验结果。

实验数据使用：


主要比较对象：

- 优化前 ep50：`runs/sis_noisy_scale_speed_ep50_20260525_151717/summary_compact.csv`
- 优化后 ep50：`runs/sis_noisy_scale_speed_ep50_fast_20260525_163138/summary_compact.csv`
- 优化前 ep20：`runs/sis_noisy_scale_speed_20260525_145652/summary_compact.csv`

## 2. 优化内容

本轮代码优化集中在训练执行效率：

1. 开启 GPU 混合精度训练：新增 `--amp --amp-dtype bf16`，在 forward/loss/eval embedding 中使用 `torch.autocast`。
2. 加速 CPU 到 GPU 数据供应：新增 `--num-workers 4 --pin-memory`，DataLoader 使用多 worker 和 pinned memory。
3. 修复多 worker 随机增强问题：每个 DataLoader worker 单独初始化 numpy RNG，避免 fork 后重复增强序列。
4. 启用固定输入形状相关优化：CUDA 训练时启用 `torch.backends.cudnn.benchmark=True` 和 `torch.set_float32_matmul_precision("high")`。
5. 增加速度记录字段：每个实验保存 `train_s`、`mean_epoch_s`、`mean_pairs_per_s`、`total_s`，每个 epoch 保存 `epoch_s` 和 `pairs_per_s`。
6. 新增规模实验脚本：`scripts/11_data_scale_speed_study.py`，可一键跑不同数据量并汇总结果。

本轮短基准还测试了 `batch_size=256`，但没有带来速度收益，短训效果也明显变差，所以最终推荐继续使用 `batch_size=128`。

推荐命令：

```bash
python scripts/11_data_scale_speed_study.py \
  --data-root /root/autodl-tmp/qkzhang_gwaug_20260522_162031 \
  --out-root runs/sis_noisy_scale_speed_ep50_fast_$(date +%Y%m%d_%H%M%S) \
  --scales 500 1000 2500 5000 10000 \
  --model-types SIS \
  --data-modes noisy \
  --backbone inceptiontime \
  --epochs 50 \
  --amp --amp-dtype bf16 \
  --num-workers 4 --pin-memory
```

主要结论：

- 训练吞吐从约 `758-767 pairs/s` 提升到约 `1835-2237 pairs/s`。

- 总耗时也下降，但不如训练耗时下降明显，因为大规模实验的候选构造、校准和匹配评估仍然是 CPU 瓶颈。

效果解读：

- `n=10000` 下优化后 `R@10=0.9930`、候选召回 `0.9947`，略高于优化前。
- `n=2500` 和 `n=5000` 的 F1 与候选召回保持在同一量级，说明速度优化没有破坏整体检索能力。
- `n=500` 小数据规模波动较大，优化后指标低于优化前，主要是小样本下训练随机性和多 worker 随机增强带来的方差更明显；论文中不应只用 n=500 判断优化效果。
- 混合精度和多 worker 会改变训练数值路径与增强顺序，因此结果不会逐位复现优化前，但高数据规模下总体效果稳定。

## 6. 论文中可写的结论

1. 训练耗时与数据规模近似线性相关，优化前后这一趋势不变。
2. `bf16 AMP + 多 worker DataLoader` 显著提高训练吞吐，尤其在 `n>=2500` 后稳定超过 `2100 pairs/s`。
3. 优化后的主要剩余瓶颈转移到 CPU 端候选构造、概率校准和匹配评估阶段；例如 `n=10000` 训练仅 `311.97s`，但总耗时为 `622.58s`。
4. 从效率-效果折中看，`n=2500` 到 `n=5000` 已经达到较高检索质量；`n=10000` 继续提升候选召回，但总时间成本更高。
5. 后续进一步加速方向应转向评估阶段：向量化候选特征构造、减少 Python 循环、并行化 candidate calibration/report、或对大规模 catalog 使用近似 Top-K 检索。
